# RoboGraphics Image Decoding (Phase 8.12)

This document is the design record for the read half of Goal 6.13. It is
normative for `RoboGraphicsDecode.h` / `RoboGraphicsDecode.c`.

Goal 6.13 wrote images. Nothing read them back: the runtime could produce a
PNG and could not consume one, which is a strange place to be when the next
thing on the roadmap is `<img>`. This phase adds the decoder.

## 1. Why it lives in RoboGraphics and not RoboHTML

An HTML document may own an `<img>`, but what an `<img>` *holds* is a
`robo_gfx_image_t`. PNG is a container format, not a document concept, and the
same decoder has to serve a screenshot path, a style sheet, a favicon and a
test fixture. Putting it under RoboHTML would have made every future caller
depend on the HTML subsystem to read a picture.

It is additive: no declaration in the frozen v1 surface changed, so
`ROBO_GRAPHICS_API_FROZEN` stays 1 while the module minor goes to 0.16.0. The
freeze pin in `SuiteRoboGraphicsPhase6.c` states that explicitly so a future
reader does not mistake the version bump for an API break.

## 2. The three entry points

```text
bytes in an unknown container
     │
     ├── robo_gfx_decode_probe(bytes, length)        what is this?
     │
     ├── robo_gfx_image_decode_info(bytes, length, limits, &info)
     │        header only — width, height, bit depth, colour type,
     │        channels, interlaced, and decoded_bytes (the RGBA8 size a
     │        decode would allocate). No pixels, no big allocation.
     │
     └── robo_gfx_image_decode(bytes, length, limits, &image)
              pixels, as a retained RGBA8 image.
```

`probe` never fails and never allocates: an empty, tiny or unrecognised run is
`CONTAINER_UNKNOWN`. `decode_info` is the budgeting call — it lets a caller
see that a file claims 4000×4000 and decide not to decode it, without ever
allocating the 64 MB that would take. `decode` is the real work.

Splitting "what is it" from "how big is it" from "give me pixels" is what lets
the HTML layer treat a hostile `src` as a state transition rather than an
allocation attempt.

## 3. What is actually implemented

**PNG**, bit depth 8, colour types:

| Colour type | Meaning | Handling |
|---|---|---|
| 0 | grayscale | replicate to RGB, alpha 255 |
| 2 | RGB | add alpha 255 |
| 3 | palette | index through PLTE, alpha from tRNS when present |
| 4 | grayscale + alpha | replicate gray, keep alpha |
| 6 | RGBA | pass through |

**DEFLATE**, in full:

- stored blocks,
- fixed-Huffman blocks,
- dynamic-Huffman blocks, including the code-length code and the repeat
  symbols 16/17/18,

with the length and distance base/extra tables from RFC 1951, and
overlapping back-references copied byte by byte so a match may point inside
itself.

**All five PNG row filters**: None, Sub, Up, Average, Paeth.

**Chunk walking** with CRC-32 verification over every chunk, across a single
IDAT or many.

### Why dynamic Huffman was not optional

The 6.13 encoder only ever emits stored blocks. A decoder that handled only
those would round-trip our own output perfectly and fail on every PNG written
by every real encoder — including the fixture a person would generate in ten
seconds to test with. "It decodes what we ourselves produce" is a test that
cannot fail for the wrong reason, so the suite decodes fixtures generated by
`python3 zlib` (dynamic Huffman, the default) as well as hand-built stored and
fixed blocks, and cross-checks against the 6.13 encoder.

## 4. What is deliberately refused

| Input | Result | Why |
|---|---|---|
| Adam7 interlaced | `ROBO_NOT_SUPPORTED` | De-interlacing is a real feature with its own test burden; refusing is safe and honest. |
| Bit depth 1/2/4 | `ROBO_NOT_SUPPORTED` | Sub-byte unpacking is a separate path; refusing is better than a wrong picture. |
| JPEG / WebP / AVIF / GIF | `ROBO_GFX_DECODE_CONTAINER_UNKNOWN` | Not sniffed at all. |
| Unknown *critical* chunk | `ROBO_NOT_SUPPORTED` | A critical chunk we do not understand may change the pixels; ancillary chunks are skipped. |
| Malformed / truncated | `ROBO_ERROR` | The file claimed something supported and then lied. |

Every refusal leaves `*out` NULL and nothing allocated. There is no path where
a bad file yields a partial image.

## 5. Hostile metadata is the normal case

Every dimension that arrives from the file is treated as hostile until it has
been checked. In order, before a single pixel byte is allocated:

1. IHDR width and height are read and validated against
   `robo_gfx_decode_limits_t` — default `max_dimension` 4096, and
   `max_decoded_bytes` 64 MiB, i.e. 4096×4096 RGBA8 with headroom. Both are
   caller policy; a zeroed struct means "defaults".
2. `width * height * 4` is computed with explicit overflow checks, and the
   result is compared against `max_decoded_bytes` — so a 100000×100000 header
   fails here, with no allocation at all, rather than at `malloc`.
3. `png_expected_raw_size` computes the filtered scanline byte count
   (including the per-row filter byte) with the same overflow discipline.
4. The IDAT stream must decompress to **exactly** that many bytes. A stream
   that runs short is truncated; one that runs long is a lie about its own
   size. Both are `ROBO_ERROR`.

The consequence is the property the Phase 8.12 security tests pin: a 16-byte
file that claims enormous dimensions fails in the header parse, and the failure
costs bounded memory rather than the claimed size.

`png_reserve_idat` grows the compressed-input buffer with its own overflow
check and caps it, so a file consisting of a million empty IDAT chunks cannot
grow memory without bound either.

## 6. Threading and lifetime

The decoder has no shared mutable state. A decode is a pure function of the
input bytes plus the limits, so any number of decodes may run concurrently and
none of them needs a lock.

The returned image follows the ordinary
`robo_gfx_image_retain` / `robo_gfx_image_release` lifetime — the decoder
returns a retained reference and owns nothing thereafter. The output is always
RGBA8 regardless of how the file stored its channels, because that is the one
format every consumer downstream already agrees on.

## 7. Test coverage

`SuiteRoboGraphicsDecode.c` (filter `graphics.decode.`, reached by
`scripts/robo test-graphics` because it is namespaced under the module's own
`graphics.` prefix), 13 tests, all against real fixtures:

| Test | What it pins |
|---|---|
| `graphics.decode.real_fixtures` | every supported colour type, and stored/fixed/dynamic DEFLATE, decode to the exact expected pixels |
| `graphics.decode.probe_safety` | signature recognition; empty/short/unrelated input → UNKNOWN; NULL and zero-length arguments on every entry point |
| `graphics.decode.rejections` | interlaced → `ROBO_NOT_SUPPORTED`; sub-byte depth → NOT_SUPPORTED; JPEG/GIF bytes → UNKNOWN |
| `graphics.decode.round_trip_encoder` | encode with the 6.13 encoder, decode, compare every pixel |
| `graphics.decode.unfilter` | a fixture exercising all five row filters decodes identically to its unfiltered twin |
| `graphics.decode.limits` | an in-limit image decodes; over-limit dimensions refuse before allocation |
| `graphics.decode.hostile_headers` / `_two` | a tiny file claiming enormous dimensions fails in the header parse at bounded cost; the arithmetic cannot wrap |
| `graphics.decode.hostile_streams` | a DEFLATE stream that runs short or long is `ROBO_ERROR`, never a partial image |
| `graphics.decode.crc_and_structure` | a corrupted chunk fails, its intact twin succeeds; truncation at any point leaves no image |
| `graphics.decode.palette` / `_malformed` | palette resolves through PLTE and tRNS; a palette index past the table is refused |
| `graphics.decode.large_rows` | wide rows and many IDAT chunks decode correctly |

Fixture bytes are generated deterministically (see
`graphics/tests/RoboGraphicsPngFixtures.h`), so the suite has no external
assets, produces the same bytes every run, and can be regenerated rather than
checked in as opaque blobs. The `dynamic` fixtures come from `python3 zlib`,
because that is what a real encoder produces and it is the case a decoder
written only against our own encoder would miss.
