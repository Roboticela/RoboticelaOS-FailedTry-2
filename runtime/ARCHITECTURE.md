# Roboticela Runtime Architecture

Independent C runtime for Roboticela OS applications and the desktop shell.

Chromium is temporary reference material only (`CHROMIUM_REFERENCE.md`).
Engineering rules: `DESIGN_RULES.md`. Allowed edges: `DEPENDENCIES.md`.

## Product shape

| Aspect | Decision |
|---|---|
| Language | C for core implementation |
| Host | Roboticela OS guest userland |
| Artifact | Freestanding ELF64 (`x86_64-unknown-none`) |
| Not | Windows `.exe`, Chromium fork, browser chrome UI |

Browser tabs, address bar, bookmarks, and Chrome-style browser windows are out of scope.
RoboHTML / RoboCSS / RoboJS / RoboDOM / RoboRender form a general application platform.

## Planned hierarchy

```text
RoboBase
  → RoboMem
  → RoboContainers
  → RoboThread
  → RoboEvent
  → RoboIPC
  → RoboPlatform
  → RoboGraphics
  → RoboWindow
  → RoboDOM
  → RoboHTML / RoboCSS
  → RoboLayout
  → RoboPaint
  → RoboRender
  → RoboDesktop
  → RoboCompositor
  → RoboJS
  → RoboAPI
  → RoboNet / RoboStorage / RoboSecurity
  → RoboShell
  → Applications
```

Lower modules never depend on higher modules.
Related services (RoboFont, RoboTLS, RoboMedia) attach beside the layer that needs them; they are not Stage 0 deliverables.

## Subsystems

For each subsystem: responsibility, allowed dependencies, modules that must not depend on it
(until a later documented exception), and the planned public C API boundary.

API names below are **planned boundaries**, not implemented headers yet (except the skeleton
`RoboticelaRuntime.h`).

the cascade *collects and orders* what applies by level, then specificity, then document order, and holds no specificity arithmetic of its own; inheritance *resolves one element* from its own cascade and an explicitly supplied parent, and never competes with the cascade; computation *normalises a value* from its declared shape and the value, and resolves nothing against a containing block, a font or the element; a colour owns nothing, is four bytes and a tag by value, and keeps `currentColor` contextual until the one layer that has an element and a parent settles it; a unit is an enumerator in a closed vocabulary whose resolution is a *question* with four answers, taken by whoever has the font metrics or the viewport — an argument, never a global; and the box model is *vocabulary and expansion only* — it knows the four sides, the three shorthands, how many components each accepts, and how a declaration distributes, and it computes no geometry, collapses no margins and resolves no containing block; and positioning is *the same shape of answer about where* — the five values and their two facts are typed and classified, while no containing block is found, no offset is applied, no rectangle exists and no stacking order is computed, so `z-index` is a number nothing compares and `position: sticky` is a value rather than a behaviour; the **margin layer** (`RoboLayoutMargin.h`) — the four declarations in four kinds (`absent`, signed `resolved`, `auto`, `unresolved`) read out of a computed style, the four **used values** a result is placed by, and the two policies (a block box's, which distributes a horizontal `auto` beside a declared width, and an atomic inline's, which turns every `auto` into zero); and the **padding layer** (`RoboLayoutPadding.h`) — the same four declarations in *three* kinds (`absent`, **non-negative** `resolved`, `unresolved`) read out of a computed style, the four used values, the **one** policy (a padding has no `auto`, so every kind of box reads the same four declarations the same way), and the two derived numbers (the width left for a box's contents, floored at zero, and the **padding box** a content box asks for, summed in 64 bits and saturated — renamed from `border_box` in 10.11, its real meaning now that a border exists); and the **border layer** (`RoboLayoutBorder.h`) — the **in-box layer between the padding and the margin**, twelve computed values over four sides, read through **three** seams because the three properties have three genuinely different computed shapes (a width is a length *or* one of `thin`/`medium`/`thick`, which the shared classification folds onto `UNUSABLE` because no other property's keyword names a length, so this reader goes to the computed style's `px`-or-keyword door rather than the generic one; a style is a closed vocabulary whose rows carry the one fact a paint phase must ask — `generates_border`, false only for `none`, because the vocabulary has ten rows and this build draws one), with the four sides each a width, a style and a colour **reused from 9.9** rather than re-invented, the whole discharged as three derived numbers — the border box (the padding box plus the border widths, 64 bits and saturated), the content width (borders and padding both subtracted, floored at zero), and the two edge policies that stay opposite because one floors and one ceilings. The **position layer** (`RoboLayoutPosition.h`) — the four inset longhands in four kinds (`absent`, **signed** `resolved`, `auto`, `unresolved`), the mode, the used **offset** record with its four counters, the one precedence rule (`left` over `right`, `top` over `bottom`, an `auto` saying nothing), the apply in 64 bits and saturated, and the object door that separates a box's **flow** position from the **final** one its result carries; and the **overflow layer** (`RoboLayoutOverflow.h`) — the property that is not about the box at all but about the **room it has**: one *value* (`visible`, `hidden`) with the axis belonging to the **property** (so `overflow-x` and `overflow-y` are two typed values and never one collapsed mode), three kinds per axis (`absent`, `resolved`, `unresolved` — declared and unusable, used as `visible` and **counted**, so a `var()`-driven boundary is visible rather than silent), one resolve policy (the longhands first, then the `overflow` **shorthand** for either axis a longhand said nothing about, then `visible`) and the used **edges** record: two modes, four **non-negative extents** measured from the padding box, and three counters that keep "declares a boundary" (`overflow_clipped`) and "has something outside it" (`overflowing`) two independent facts. The phase's one structural decision is that an overflow is **not a size**: the box keeps the size its declarations and its contents asked for, and what is added is a second rectangle *beside* it — the **region** (the padding box grown by the extents and clipped back on an axis whose mode clips), which is what a **parent** folds in through `robo_layout_overflow_edges_include` (a per-side maximum in 64 bits and saturated, so a `region` wholly inside the padding box leaves every extent where it was), and the **clip rectangle** (the padding box, refused with `ROBO_NOT_FOUND` when neither axis clips), which is what a **paint** pass will clip to. And the **invalidation layer** (`RoboLayoutInvalidation.h`) — the one header that is not about a box's geometry but about **which of those conclusions are still true**, since geometry is a function of *ancestors'* conclusions and a leaf whose author changed nothing still moves when its parent's padding does: four **state bits** that compose (`STYLE` for a change layout does not read, `LAYOUT` for a box's own stale geometry, `SUBTREE` for its descendants', `OVERFLOW` for its measurement alone, with `CLEAN` the 0 a cleared record already is), seven **reasons** answering "what happened?" where the bits answer "what is stale?", and **three** masks rather than one because the three questions have three different answers (`LAYOUT_BITS` for *must a pass run*, `OWN_BITS` — `LAYOUT` alone — for *where would it start*, `ALL` for *is anything owed*); a property-**name** classifier (`NONE` / `PAINT` / `GEOMETRY`) written out by hand because only this module can say what *layout* reads, and it is wrong in both directions if cheapened — `border-style` is geometry (10.11's used width is zero unless the style draws) and an unknown name is nothing rather than everything; **three** marking policies whose shapes differ (a box-model change marks the box, its ancestors' measurement and the *transitively* following flow; a displacement marks the same and **leaves the following flow clean**, which is 10.12's contract made testable; an overflow-mode change marks measurements alone and no geometry); the dirty root computed as the **lowest common ancestor** of the boxes whose own geometry is stale rather than the shallowest such box, because a following sibling can sit higher in the tree than the change; and the two doors a consumer must keep apart (`robo_layout_tree_is_clean` and `robo_layout_tree_needs_layout`, since *not clean* and *need layout* are not the same statement). Folding a child's *contents* in rather than its **region** is the mistake that compiles and leaks a clipped subtree into an ancestor's area, which is why the recursion is stated once and asserted with a clipping child — **10.3 computes the block direction and 10.4 the inline one**, as one pass with two branches: an inline formatting context's contents are placed along a line, wrapping when one does not fit, with an atomic inline's contents laid out inside it by the block pass and a transparent inline box written as the **union** of what its contents reached. **10.5** widens the object vocabulary for the first time — a text node is not an element and has no `display` to derive from, so `ROBO_LAYOUT_OBJECT_TEXT` is the one justification 10.1 wrote down that a second kind satisfies — and makes a run an ordinary participant whose width comes from a callback, a pass with none measuring every run as zero and **counting** it. **10.6** turns the line into a record a caller reads back: identity, an ordinal within its context, a finalized rectangle in the owner's content-box space, the width it had to fit, and the objects it placed — where a transparent inline box with contents is a participant of the context and a member of **no** line, because its rectangle is a union. **10.7** gives every line a **floor** — an ascent, a descent and the kind they came from, folded as the members' maxima while they are placed — and places each member *on* it, writing each member's `y` in one walk at finalization because the maximum is not final until the last placement; the same phase moves the union to a post-order walk over the finished context, since a box's rectangle bounds positions that are no longer final when it closes. **10.8** is where a box's `size` stops having one rule: the width is resolved first — the declared one, or the containing block's for `auto` — the box's children are laid out **into that width**, and the height is resolved afterwards as a declared `px` length or the contents' extent; an atomic inline cannot use that pair, because its `auto` height is the extent of contents that could only have been laid out *at* a width, so it resolves width, walks its contents, and asks for height last. A percentage, a relative unit or an intrinsic keyword is read, recorded as **unresolved**, and filled from the available space with a source saying so — never a zero, and never a guess. Every percentage and relative unit *as a length*, shrink-to-fit and the intrinsic keywords, `min-width`/`max-width`/`min-height`/`max-height` as *properties* (the sizing layer has bounds and clamps through them, but RoboCSS registers none of the four yet), `box-sizing` (a `border-box` model is one branch a later goal adds), a percentage padding (read, counted unresolved and used as zero), padding on a **transparent inline box**, a **border**, positioning, overflow, `line-height` as a resolved used value, `vertical-align`, shaping, bidi, Unicode line breaking, fragmentation and the anonymous box are absent by design, and `robo_layout_result_state` is the per-box authority on whether geometry exists. **10.9** adds the first number in the module that is *not* a size: a box's position becomes its **margin origin** — its containing block's content origin plus its own `margin-top` and `margin-left` — while its `size` is untouched by any margin, and what a parent stacks its next child below becomes the **margin box**, `top + height + bottom`. The four margins resolve *before* the width, because an `auto` width fills what they left; a horizontal `auto` takes its share of the leftover beside a declared **definite** width, an odd pixel going to `right`, while a vertical `auto` is zero (it means something only for an absolutely positioned box, 10.12) and every `auto` on an atomic inline is zero; a negative marginal is legal and kept **signed**, which is the one respect the margin vocabulary differs from the sizing one. What it does **not** claim is CSS's *group* semantics: a subtree is not composited into a flattened layer, the strength is applied **per drawing**, and the difference is **asserted rather than hidden** (`paint.opacity.group_deviation` computes both answers through the same blend door) — closing it needs an offscreen layer, which is a compositor. Version **0.8.0**, `opacity` **1**, `raster` still **0**. And **11.10** asks the same tree the **inverse** question — which node is drawn at this point — and it is the first facility in this module that answers rather than draws: the answer is assembled entirely from records the earlier releases established (the geometry from `robo_paint_boxes_of`, the boundary in force from 11.8's clip record, the strength in force from 11.9's), and it lives in RoboPaint rather than in a module beside it because it is a second consumer of those two records *and of the walk* — the painter accumulates a page origin, narrows a boundary and multiplies a strength while descending, and the hit test accumulates the same three things in the same order from the same declarations, which is what makes "the two agree about a document" an assertion instead of a coincidence. Four rules, each mirroring the painter: **last drawn wins** (children before their parent and the last child before the first, because the node that covers a point is the last one drawn there — a document-order walk answers with the box underneath, which is the classic hit-test bug, and the case that catches a merely-reversed walk is three overlapping siblings where the *middle* one is on top); **a box's region is its border box** (the union of everything it could paint into, so CSS hits a transparent `div` over all of it, while an **empty** rectangle contains no point, not even its own corner); **the boundary clips the contents and never the box** (11.8's arrangement read backwards: the box is entered under the boundary in force and its children under the boundary its own `overflow` puts in force, so a `overflow: hidden` ancestor's child outside the boundary is not hit while that ancestor's own border band still is); and **a strength does not gate** (`opacity: 0` is still hit, because CSS governs this with `pointer-events` and this build has none — the strength travels in the result anyway, so the goal that adds the property has the number). The **outcome** is a vocabulary rather than a boolean and its third member is `STALE`: a tree that needs layout makes the query **refuse**, for the reason the paint pass refuses one, since an answer assembled from half-computed geometry is not a less accurate answer but a **wrong** one — and it is an outcome, not an error, so the query returns `ROBO_OK` for it. The answer is a **value** (the id, both coordinate spaces, the three rectangles, the boundary and the strength copied in) rather than a reference, so a mutation cannot rewrite a conclusion already drawn, and it carries the **DOM handle** as well as the layout id because the layers above consume the handle while the id is what validates. The **counters** carry three identities, the load-bearing one being that a `MISS` must have excluded the point for a reason. The **trace** is the walk's control flow — one line per examined object, with `enter`/`unplaced`/`region`/`clip`/`hit` and **no** reason for "tested and not the answer", deliberately — and the dump runs the query twice rather than recording a trace, which is sound because the walk is a pure function of the tree and the point. The phase's claim is checked three ways: against the **painter's own records** (the suite takes every coordinate from the `BEGIN_BOX`/`TEXT` record for the node in question rather than from a literal), against **itself** (repeated queries, mutation isolation), and against the **screen** — three opaque boxes, two of them overlapping because `position: relative` moved one onto the other, painted into a real surface, with every probe checked in both directions so that the answer's own fill, read from the paint list, *is* the pixel; the miss probe's control is an **unpainted** pixel. Version **0.9.0**, `hit_testing` **1**, `raster` still **0** — the sixth capability field, and the first in this module that is not about drawing, so the two do not move together. And **11.11** answers the question the ten releases before it raised and could not answer — given a picture this module already produced, **which of its pixels are no longer the pixels the document describes?** — as a **set of regions** rather than as a mechanism, which is the release's central decision: 11.1 recorded that a paint list is *not a cache of conclusions* but is regenerated from the tree on every pass, and this goal crosses the line that record drew **without** turning the list into a cache, because the display list is still rebuilt whole and the set says how little of it a caller may re-execute — with the input 11.1 left behind (`robo_paint_stats_t.style_only`) now the module's **coarsest door** (`set_from_stats` answers *nothing owed* for a zero count and one whole-extent region otherwise) rather than a promise about a future one. `robo_paint_invalidation_region_t` is the first record in this module whose whole purpose is to **survive a mutation** — a rectangle, a node, a reason, the boundary in force and two flags: `narrowed` (the rectangle *is* the intersection with its boundary) and `full` (a conservative whole-extent answer), neither inferable from the rectangle — and the rule the whole module runs on is that **a region promises a repaint of it is *sufficient*, never that those pixels changed**: every door widens when it is not certain and narrows only against a boundary it can **read**, because the failure mode the goal was written against is a **missing** rectangle and a repaint list cannot recover from one, which is also why a change a producer cannot place becomes a whole-extent region rather than a guess. **Only records that paint produce regions** — a marker, a content boundary or a scope draws nothing, so a region out of its box would be a rectangle with nothing stale inside it — and the scopes are not lost by that rule because every record **inside** a scope carries the scope's boundary in its own `clip` and its strength in its own `opacity`, so a clip that moves and an element that fades reach the set through the drawings they bound while the structural positions are still **counted** (`compared`/`matched`/`differed`/`inserted`/`removed` remain claims about the walk). A **move is two rectangles**, and which doors union them is not an inconsistency but the phase's sharpest decision: `add_change` stores the **union**, because the caller vouched that both rectangles came from one thing, while `mark_node_change` and the diff store **two**, because the two were drawn under boundaries that need not be the same — a box that moved out of an `overflow: hidden` ancestor — and one union narrowed by one of them would repaint the middle of a move under a boundary describing only one end of it. A **parent's strength change invalidates the descendants' rectangles**, which 11.9's accumulation makes free (the strength is carried on every record, so the subtree is found with no compositor and no damage tree; `set_mark_subtree` is the explicit door for the same fact). Three vocabularies are new: eleven **reasons** — one per *decision* rather than one per property, each with a producer in the module, and **no `VISIBILITY`** reason because a property no layer consumes cannot change a pixel; three **classes** — `classify_property` answers `NONE`/`PAINT`/`LAYOUT`, derived from RoboLayout's classifier rather than restated, so the three properties layout calls paint-visible while **no layer draws from** them (`visibility`, `text-decoration`, `background-image`) answer `NONE` rather than sending a caller to repaint an identical picture; and three **scopes** — `NONE`/`PARTIAL`/`FULL`, the distinction a caller acts on. Ten producers fill the set (an explicit rectangle, an old-and-new pair, a record, a node, a subtree, a node pair, the whole extent, the two artifact diffs and the pass record), all reading geometry out of the artifact rather than re-deriving it; the set is **owned and growable**, iterated in insertion order with **no hash table anywhere** (the order is a function of the document and the artifacts, never of an address or a clock — two independent trees produce equal sets **and equal dumps**), refuses a zero-area region by one rule in one door and **counts the refusal** (`excluded`, the number that tells "nothing changed" from "everything changed outside the boundary"), and carries **eleven counters with three identities** (`added = narrowed + conservative`, `compared = matched + differed`, and `excluded` the regions *not* in the set). Version **0.11.0** with `paint_invalidation` flipped from the **0** 11.1 declared it with, `raster` now the only field still **0** (a region says a repaint of it is sufficient; nothing here executes one), a new `ROBO_PAINT_DOMAIN_INVALIDATION` domain (count 13) and fourteen suite files over **232** cases — the 29 new ones all built from **two states of one document**, with two at the **pixel**: every differing pixel lies inside a region, and clearing the regions of the first frame and painting the second into it reproduces a full render of the second **byte for byte**. And **11.12** adds one door to this module rather than a second module's worth of work, because the walk is the thing that must not exist twice: `robo_paint_decoration_paint_bounded` is `robo_paint_decoration_paint` with a rectangle — the same order, the same clips, the same strengths, the same drawings, with every drawing additionally clipped to the bound — and `bounded_out` counts the drawings whose rectangle missed it (a statement about **work**, not pixels, and a subset of `draws`, so `commands = draws + skipped` still holds exactly). The bound is a **clip and not a filter**, which is the phase's decision and not an implementation detail: a text run's rectangle is its advance box and a glyph's ink can overhang it, so skipping a command whose rectangle misses the bound would put a hole in the picture that no count would catch. `raster` — the field 11.1 declared and left **0** through ten releases — flips to **1** at version **0.12.0**, and the claim it makes is narrower than it reads: RoboRender **executes** a whole list into a target, while this module's own walk still neither owns a target nor clears one. **11.13** gave this layer a fourth reader and no new door: RoboDesktop executes a window's list through RoboRender into the window's own target, so a shell window's contents are bounded by the target's rectangle — a document's clip can no longer reach the panel, and the wall a boundary or a strength would have to get past grew by one. Next: **Phase 12 — event dispatch**, which gives 11.10's hit test a consumer that acts on its answer. |

|---|---|

| **Public C API boundary** | `Include/RoboRender/RoboRender.h` — the owned `robo_render_target_t` with its fifteen doors (facts, bytes, checksum, equality, clear, surface), the `robo_render_frame_t` record with its three doors, `robo_render_rasterize` and `robo_render_rasterize_regions`, the frame dump (`robo_render_frame_write`), the presenter (`RoboRenderPresenter.h`: `present_region`, `present`, `present_framebuffer`, the presentation record and its four-line dump), and the sixteen-flag capability table with the module's version and `robo_render_rasterization_is_implemented()`. |
| **Status** | Goals **11.12** and **11.13** complete — **rasterization** and **presentation** (`render/README.md`, `render/docs/`): three suite files over **31 cases** (seven of them 11.13's presenter), plus one door added below the module (`robo_paint_decoration_paint_bounded`). The module turns a display list into **pixels in a buffer it owns**: `robo_render_target_create` makes a write-capable **RGBA8** surface and the run executes the whole command vocabulary — backgrounds, border bands, a run's glyphs, an image — in the list's order, bounded by its clip scopes and at the strengths its opacity scopes establish, with **no state of its own between calls** (there is no `begin`/`draw`/`end` and no `SAVE_STATE`/`RESTORE_STATE`, because a command carries the boundary and the strength it is drawn under). The target is **zero-filled** and a run **never clears** it: clearing is the caller's (`robo_render_target_clear`), because a region run must not erase the pixels its regions were computed to preserve. A **preflight** walks the list once before the first pixel and refuses an unknown command kind or an unbalanced scope pair, so a returned `ROBO_OK` means the whole list was drawn and a refusal leaves the target exactly as it was found. A **region run** takes a paint invalidation set, executes the list **once** over `set_bounds` (one run, never one per region — overlapping regions would composite a semi-transparent drawing twice) and narrows the raster's **clip** to it, so a bounded pass equals a full frame inside the region — asserted byte for byte. An **empty or NULL set** is success with nothing done, which is 11.11's own "the picture is current". `robo_render_target_bytes`/`_checksum`/`_equal` make determinism checkable and the seven-line frame dump carries **no address**. 11.13 gave that buffer an **exit** and changed nothing else: `robo_render_present` composites a frame into a destination **surface** the caller owns (never a window id and never a QEMU mapping — a rasteriser that could reach RoboWindow could not be tested without one), at an offset, **clipped rather than refused** when it does not fit, with a record whose `presented_pixels + clipped_pixels` sum to the frame's own count and a validity rule that refuses one that claims `complete` for a frame that lost pixels; `present_region` answers the same arithmetic without writing, and `present_framebuffer` takes RoboGraphics' framebuffer by borrowing a surface for the duration of the call. **Version 0.2.0**, `ROBO_RENDER_API_FROZEN=0`, `ROBO_RENDER_RASTERIZATION_IMPLEMENTED=1`, `ROBO_RENDER_PRESENTATION_IMPLEMENTED=1`; and the module has **no lifecycle** — it holds no global state, so there is no `init`/`shutdown` pair and no `is_initialized`. The capability table was **ten 1s and six 0s** in 11.12 and is **eleven 1s and five 0s** since 11.13, which moved `presentation` and nothing else: `compositor` (a set of frames with an ordering), `tiles` (region *subtraction*, which 11.11 refused), `damage_tracking` (a history with a lifetime), `frame_scheduling` (a clock, a deadline and a queue — absent, and the determinism depends on it) and `gpu` (a module, not a branch). A presentation *system* would be a `compositor` with pacing, which is why `presentation`'s release note says the claim is a call and not a system. Transforms, filters, masks, blend modes beyond source-over, `border-radius`, gradients, antialiasing, text **shaping** and any image **loading** are not rows at all: they are properties the display list would have to carry and the graphics raster would have to implement, and both are named where they belong. Next: **Phase 12 — event dispatch**, which consumes 11.10's hit test rather than replacing it. |
